## 1. 设计目标与选型理由

### 1.1 为什么设计 TagBus

Modbus RTU 在工业界广泛使用，但它有两个根本性弱点：

| 弱点 | Modbus RTU | TagBus |
|------|-----------|--------|
| **自描述性** | 无——主机需预知寄存器映射和类型 | 标签自带名称、类型、扩展属性 |
| **数据类型** | 仅 16-bit 寄存器（需手动拼 float/string） | 原生 13 种类型（bool~float64+string） |

TagBus 的设计目标：**在 RS-485/UART 物理层上，提供即插即发现、类型安全的标签读写能力**。

### 1.2 核心设计原则

1. **帧定界用标记而非静默间隔**——Modbus 的 3.5 字符静默间隔在 USB-CDC 隧道中不可靠；帧头 `0xA55A` + 长度 + 帧尾 `0x7E7E` 在任何链路上都可靠。
2. **值长度 <u>1 字节</u>**——与标签发现（扩展属性）分开优化：传输高频的值数据时省 1 字节/条；扩展属性保持充裕空间。
3. **CRC 覆盖 [设备ID..载荷末尾]**——包含地址信息，防止帧头误匹配后的数据被当作有效帧。
4. **广播写不回复**——与 Modbus 广播语义一致，用于批量配置多台设备。

### 1.3 为什么不选其他方案

| 方案 | 不适用原因 |
|------|-----------|
| Modbus RTU | 无类型信息，float 需手动拼 2 个寄存器；无自发现 |
| CANopen | 需要 CAN 控制器，硬件成本高；对象字典设计复杂 |
| OPC-UA | 代码体积 100KB+，不适合嵌入式 |
| Protobuf + UART | 需 COBS 等帧定界层；变长编码在嵌入式解析开销大 |

## 2. 帧格式

### 2.1 基本帧结构

```
┌────────┬────────┬────────┬──────────┬──────────┬────────┬────────┐
│  帧头   │ 设备ID │ 功能码  │ 载荷长度  │   载荷    │ CRC16  │  帧尾   │
│  2B    │  2B    │  1B    │   2B     │   nB     │  2B    │  2B    │
└────────┴────────┴────────┴──────────┴──────────┴────────┴────────┘
```

| 字段 | 大小 | 说明 |
|------|------|------|
| `帧头` | 2 | 固定值 `0xA55A`，小端字节序（UART 先发 `0x5A` 再发 `0xA5`） |
| `设备ID` | 2 | 目标设备地址，小端序；`0xFFFF` 为广播地址 |
| `功能码` | 1 | 命令类型，见 [功能码总览](#5-功能码总览) |
| `载荷长度` | 2 | 载荷字节数，小端序，范围 0..1024 |
| `载荷` | n | 功能码特定的数据 |
| `CRC16` | 2 | CRC-16 (Modbus)，覆盖 [`设备ID`..`载荷末尾`]，小端序 |
| `帧尾` | 2 | 固定值 `0x7E7E`，小端序 |

**帧总长度 = 11 + 载荷长度**，最小 11 字节，最大 1035 字节。

### 2.2 字节序

**全链路统一小端（LE）**，RP2350 原生字节序，零开销。

| 数据 | 字节序 | Python struct |
|------|--------|---------------|
| 帧头/帧尾 | 小端 | `'<H'` |
| 设备 ID | 小端 | `'<H'` |
| 载荷长度 | 小端 | `'<H'` |
| 标签 ID | 小端 | `'<H'` |
| 计数 (count/total) | 小端 | `'<H'` |
| CRC16 | 小端 | `'<H'` |
| int/float 值 | **小端** | `'<h'`, `'<i'`, `'<f'` 等 |

> 帧头 `0x5A 0xA5`（小端），float32 26.0 = `00 00 D0 41`（小端）。

## 3. 帧定界与同步恢复

### 3.1 定界策略

帧头 `0xA55A` 和帧尾 `0x7E7E` 的两个字节组合是故意选取的：
- `0xA5` = 10100101，`0x5A` = 01011010（互为按位取反），自相关性极低
- `0x7E` = 01111110，`0x7E7E` 在随机数据中概率约 1/65536

`载荷长度` 字段提供第二层定界——接收方在帧头后读取长度，跳转到 CRC 位置验证，再核对帧尾。三重检查同时通过才认为收到有效帧。

### 3.2 同步恢复流程

```
1. 逐字节扫描 0xA5 0x5A（帧头）
2. 找到帧头后，读偏移 5-6 的 载荷长度
3. 跳转到 偏移7 + 载荷长度 + 2 处验证 CRC
4. 核对 CRC 后 2 字节是否为 0x7E 0x7E（帧尾）
5. 全部通过 → 有效帧；任一失败 → 回到步骤 1
```

### 3.3 半双工 RS-485 注意事项

RS-485 收发切换后会有线路稳定时间。建议在发送帧头前插入 2-3 字节的导言（如 `0xFF 0xFF`），让接收方 UART 硬件对齐。TagBus 协议本身不规定导言字节，由物理层实现处理。

## 4. CRC16

- **多项式**：`0x8005`（Modbus 兼容）
- **初始值**：`0xFFFF`
- **反射输入/输出**：是（与 Modbus 一致）
- **计算范围**：`[设备ID(2B) + 功能码(1B) + 载荷长度(2B) + 载荷(nB)]`
- **结果存储**：小端序（低字节在前）

> CRC 不覆盖帧头和帧尾，因为这两个字段用于帧同步——若帧头/帧尾出错，接收方无法定位帧边界，CRC 验证也失去意义。

## 5. 功能码总览

| 码值 | 名称 | 方向 | 广播 | 说明 |
|------|------|------|------|------|
| `0x01` | 读标签列表 | 读 | 否 | 获取标签元数据（支持分页） |
| `0x02` | 读输入标签 | 读 | 否 | 批量读取只读标签的当前值 |
| `0x03` | 读保持标签 | 读 | 否 | 批量读取可读写标签的当前值 |
| `0x05` | 写保持标签 | 写 | **是** | 批量写入标签值；广播时不回复 |
| `0x06` | 获取设备信息 | 读 | 否 | 获取厂商/型号/固件版本/标签统计 |
| `0x07` | 心跳/状态 | 读 | 否 | 查询设备健康状态与运行统计 |

## 6. 数据类型

### 6.1 类型编码表

类型编码与 [NSON](https://github.com/nson-format) 二进制格式保持一致：

| 编码 | 类型 | 值长度 | NSON 名 | 说明 |
|------|------|--------|---------|------|
| `0x01` | bool | 1 | BOOL | `0x00` = false, `0x01` = true |
| `0x02` | null | 0 | NULL | 值不存在/不可用（传感器断线等） |
| `0x11` | float32 | 4 | F32 | IEEE 754 小端 |
| `0x12` | float64 | 8 | F64 | IEEE 754 小端 |
| `0x13` | int32 | 4 | I32 | 小端 |
| `0x14` | int64 | 8 | I64 | 小端 |
| `0x15` | uint32 | 4 | U32 | 小端 |
| `0x16` | uint64 | 8 | U64 | 小端 |
| `0x17` | int8 | 1 | I8 | |
| `0x18` | uint8 | 1 | U8 | |
| `0x19` | int16 | 2 | I16 | 小端 |
| `0x1A` | uint16 | 2 | U16 | 小端 |
| `0x21` | string | n | STRING | UTF-8，n ≤ 255 |
| `0x22` | bytes | n | BINARY | 原始二进制，n ≤ 255 |
| `0x41` | timestamp | 8 | TIMESTAMP | Unix 时间戳（秒），u64 小端 |
| `0x42` | id | 12 | ID | 唯一标识符：ts[6] + count[2] + random[4] |

> NSON 还定义了 `ARRAY(0x31)`、`MAP(0x32)`，TagBus 暂不支持。

### 6.2 类型校验

写请求时，设备端校验：
- 固定长度类型：实际值长度必须等于声明长度
- 变长类型（string/bytes）：实际值长度必须 ≤ 255
- 类型编码必须已知（0x01-0x0D）

校验失败返回 `STATUS_TYPE_MISMATCH (0x03)`。

## 7. 状态码

| 码值 | 名称 | 含义 |
|------|------|------|
| `0x00` | OK | 操作成功 |
| `0x01` | NOT_FOUND | 标签 ID 不存在 |
| `0x02` | READ_ONLY | 尝试写入只读标签 |
| `0x03` | TYPE_MISMATCH | 值长度与标签类型不匹配 |
| `0x04` | OUT_OF_RANGE | 值超出扩展属性定义的 min/max |
| `0x05` | WRITE_FAILED | 硬件写入失败 |
| `0x06` | UNKNOWN_FUNC | 不支持的功能码 |

## 8. 广播机制

### 8.1 广播地址

设备 ID = `0x0000` 或 `0xFFFF` 视为广播地址。

### 8.2 广播行为

| 功能码 | 广播行为 |
|--------|----------|
| `0x05` 写保持标签 | **执行写入，不回复** |
| 所有读命令 | **忽略**（广播读无意义） |

> 与 Modbus 广播语义一致：广播仅用于写，防止所有设备同时回复导致总线冲突。

### 8.3 典型用例

```
主机 → 广播 0xFFFF: 写标签 300 (采样周期) = 1000ms
→ 总线上所有设备同时更新采样周期，无回复
```

## 9. 标签元数据结构

### 9.1 标签属性

标签在设备端以结构化方式存储，通过 `0x01` 读标签列表命令对外发布：

```
每个标签的元数据:
  ID(2B) + 类型(1B) + 访问(1B) + 名称长度(1B) + 名称(nB) + 扩展长度(1B) + 扩展(nB)
```

| 字段 | 大小 | 说明 |
|------|------|------|
| ID | 2 | 标签唯一标识符，小端序 |
| 类型 | 1 | 数据类型编码（见 [数据类型](#61-类型编码表)） |
| 访问 | 1 | `0x01` = 只读, `0x02` = 可读写 |
| 名称长度 | 1 | 名称的 UTF-8 字节数 |
| 名称 | n | 标签名称（UTF-8），≤ 32 字节 |
| 扩展长度 | 1 | 扩展属性的字节数 |
| 扩展 | n | 键值对字符串，≤ 64 字节 |

### 9.2 扩展属性格式

扩展属性使用 `key:value` 逗号分隔格式：

| 示例 | 说明 |
|------|------|
| `unit:℃` | 单位 |
| `min:10,max:35` | 取值范围 |
| `0:关,1:开` | 枚举值说明 |

> 当前扩展属性为纯字符串。未来可考虑 TLV 结构化格式（不兼容）。

## 10. 功能码详细定义

### 10.1 0x01 — 读标签列表（分页）

#### 请求

```
start(2B) + count(2B)
```

| 字段 | 说明 |
|------|------|
| start | 起始索引（0-based），小端序 |
| count | 返回数量，0 表示从 start 开始全部 |

#### 响应

```
total(2B) + start(2B) + count(2B) + [标签元数据] × count
```

| 字段 | 说明 |
|------|------|
| total | 设备标签总数 |
| start | 实际起始索引 |
| count | 实际返回数量 |

#### 分页示例

```
设备有 50 个标签:

请求: start=0,  count=20  → 返回标签 0~19
请求: start=20, count=20  → 返回标签 20~39
请求: start=40, count=20  → 返回标签 40~49
请求: start=0,  count=0   → 返回全部 50 个
```

---

### 10.2 0x02 — 读输入标签

只读标签的批量值查询。

#### 请求

```
count(2B) + [ID(2B)] × count
```

#### 响应（每个标签）

```
count(2B) + [ID(2B) + status(1B) + value_len(1B) + value(nB)] × count
```

| 字段 | 说明 |
|------|------|
| status | `0x00`=成功，非零=错误码 |
| value_len | 值字节数（1 字节） |
| value | 小端字节序的值 |

#### 示例：读温度 (ID=100, float32) + 湿度 (ID=101, float32)

```
请求载荷: 0002 0064 0065
         ──── ──── ────
         数量=2 ID=100 ID=101

响应载荷: 0002
         0064 00 04 0000D041    ← ID=100, 成功, 长度4, 26.0℃
         0065 00 04 00004842    ← ID=101, 成功, 长度4, 50.0%
```

---

### 10.3 0x03 — 读保持标签

可读写标签的批量值查询。格式与 `0x02` 完全一致。

若请求的 ID 对应一个只读标签，该条目返回 `status=READ_ONLY (0x02), value_len=0`。

---

### 10.4 0x05 — 写保持标签

#### 请求

```
count(2B) + [ID(2B) + value_len(1B) + value(nB)] × count
```

> `value_len` 为 1 字节，单值最大 255 字节。

#### 响应

```
count(2B) + [ID(2B) + status(1B)] × count
```

#### 示例：写加热开关 (ID=201, bool=true) + 设定温度 (ID=200, float32=28.0)

```
请求载荷: 0002
         00C9 01 01              ← ID=201, 长度1, true
         00C8 04 0000E041        ← ID=200, 长度4, 28.0

响应载荷: 0002
         00C9 00                 ← ID=201, 成功
         00C8 00                 ← ID=200, 成功
```

#### 广播写

设备 ID = `0xFFFF` 时，设备执行写操作但**不发送响应**。

```
请求: A55A FFFF 05 0007 0001 00C8 04 0000E041 CRC 7E7E
      ──── ────
      帧头  广播  写   载荷=7  1标签 ID=200 长度4 28.0

→ 所有设备写入设定温度=28.0，无一回复
```

---

### 10.5 0x06 — 获取设备信息

#### 请求

无载荷（载荷长度 = 0）。

#### 响应

```
protocol_ver(2B) + vendor_id(2B) + product_id(2B)
+ firmware_year(2B) + firmware_month(1B) + firmware_day(1B)
+ ro_tag_count(2B) + rw_tag_count(2B)
+ name_len(1B) + name(nB)
```

| 字段 | 说明 |
|------|------|
| protocol_ver | `[主版本, 次版本]`，当前 `[2, 0]` |
| vendor_id | 厂商编号，小端 |
| product_id | 设备型号，小端 |
| firmware_year | 固件年份，小端 |
| firmware_month | 固件月份 |
| firmware_day | 固件日期 |
| ro_tag_count | 只读标签数量 |
| rw_tag_count | 可读写标签数量 |
| name_len | 设备名称字节数 |
| name | 设备名称（UTF-8） |

#### 示例

```
请求: A55A 0001 06 0000 CRC 7E7E

响应载荷: 0200 0100 0200 E407 01 01 0300 0200 0C 54616742757320446576696365
          ──── ──── ──── ──────── ── ── ──── ──── ── ─────────────────────
           v2.0 厂商1 型号2  2024  1月 1日 RO=3 RW=2  12  "TagBus Device"
```

---

### 10.6 0x07 — 心跳/设备状态

#### 请求

无载荷。

#### 响应

```
status(1B) + uptime(4B) + rx_count(4B) + tx_count(4B) + error_count(4B)
```

| 字段 | 大小 | 说明 |
|------|------|------|
| status | 1 | `0x00`=正常, `0x01`=告警, `0x02`=故障 |
| uptime | 4 | 设备运行秒数，小端 |
| rx_count | 4 | 成功接收的有效帧数，小端 |
| tx_count | 4 | 成功发送的响应帧数，小端 |
| error_count | 4 | 累计错误帧数（CRC 错误 + 格式错误），小端 |

#### 心跳检测逻辑

```
主机每 1~5 秒发送一次心跳:
  ① 发送 0x07 → 收到响应且 uptime 递增 → 设备正常
  ② 连续 3 次无响应 → 设备离线
  ③ error_count 增长 → 线路干扰或设备异常
```

## 11. 设备端处理流程

### 11.1 写请求校验链

```
写请求处理流程（0x05）:
  1. 解析 ID(2B) + 值长度(1B) + 值(nB)
  2. 查找标签: ID 存在？
     └─ 否 → STATUS_NOT_FOUND (0x01)
  3. 检查属性: 标签是 RW？
     └─ 否 → STATUS_READ_ONLY (0x02)
  4. 检查长度: 值长度 == 类型期望长度？
     └─ 否 → STATUS_TYPE_MISMATCH (0x03)
  5. 检查范围: 值在扩展属性定义的 min/max 内？
     └─ 否 → STATUS_OUT_OF_RANGE (0x04)
  6. 写入硬件: 成功？
     └─ 否 → STATUS_WRITE_FAILED (0x05)
  7. 返回 STATUS_OK (0x00)
```

### 11.2 广播处理

```
收到帧:
  1. 帧头/帧尾/CRC 校验
  2. 设备 ID 匹配 → 处理
  3. 设备 ID = 0xFFFF → 仅 0x05 处理（不回复），其余忽略
  4. 其他 → 静默丢弃
```

## 12. 通信示例

### 场景：温控器监控

设备 ID = `0x0001`，6 个标签：3 个 RO（温度/湿度/状态）+ 2 个 RW（设定温/加热）+ 1 个 RO（设备名）。

```
① 主机获取设备信息
  请求: A55A 0001 06 0000 CRC 7E7E
  响应: A55A 0001 06 0013 0200 0100 0200 E407 0101 0300 0200 0C
        54616742757320446576696365 CRC 7E7E
        → 协议v2.0, 厂商1, 型号2, 固件2024.01.01
          RO=3个, RW=2个, 名称="TagBus Device"

② 主机分页读取标签列表 (页1: 前3个)
  请求: A55A 0001 01 0004 0000 0003 CRC 7E7E
        start=0 count=3

  响应: A55A 0001 01 0045 0006 0000 0003
        0064 11 01 06 E6B8A9E5BAA6 06 756E69743AE28483
        ├─ ID=100 float32 RO 名称="温度" 扩展="unit:℃"
        0065 11 01 06 E6B9BFE5BAA6 05 756E69743A25
        ├─ ID=101 float32 RO 名称="湿度" 扩展="unit:%"
```

## 13. 上位机实现指南

### 13.1 最小实现步骤

```
1. 打开串口 (115200 8N1)
2. 循环:
   a. 逐字节喂入帧解析器
   b. 扫描 0xA5 0x5A → 读长度 → 验证 CRC → 核对 0x7E 0x7E
   c. 有效帧 → 派发到对应功能码处理器
3. 首次连接:
   a. 发送 0x06 获取设备信息
   b. 发送 0x01 (count=0) 获取全部标签元数据
   c. 根据标签列表构建轮询表
4. 运行:
   a. 周期发送 0x02/0x03 读取标签值
   b. 按需发送 0x05 写入标签值
   c. 周期发送 0x07 检测设备在线
```

### 13.2 帧构建伪代码

```python
def build_frame(device_id: int, func: int, payload: bytes) -> bytes:
    header = struct.pack('<H', 0xA55A)
    dev = struct.pack('<H', device_id)
    plen = struct.pack('<H', len(payload))

    crc_data = dev + bytes([func]) + plen + payload
    crc = modbus_crc16(crc_data)

    footer = struct.pack('<H', 0x7E7E)
    return header + crc_data + struct.pack('<H', crc) + footer
```

### 13.3 字节序注意事项

| 数据 | 字节序 | Python struct |
|------|--------|---------------|
| 帧头/帧尾 | 小端 | `'<H'` |
| 设备 ID | 小端 | `'<H'` |
| 载荷长度 | 小端 | `'<H'` |
| 标签 ID | 小端 | `'<H'` |
| 计数 (count/total) | 小端 | `'<H'` |
| CRC16 | 小端 | `'<H'` |
| **int/float 值** | **小端** | `'<h'`, `'<i'`, `'<f'` 等 |

### 13.4 错误处理

```
发送请求 → 等待响应:
  超时 (如 500ms):
    → 重试 1 次
    → 仍超时 → 标记设备离线

  收到响应但 CRC 错误:
    → 丢弃此帧，等待重传

  收到响应 status ≠ 0:
    → 根据状态码决定处理策略（见第 7 节）
```

## 14. 与 Modbus RTU 对比

| 维度 | Modbus RTU | TagBus v4.1 |
|------|-----------|-------------|
| **物理层** | RS-485 / UART | RS-485 / UART |
| **帧定界** | 静默间隔 3.5 字符 | 帧头 `0xA55A` + 帧尾 `0x7E7E` |
| **地址范围** | 1-247 | 1-65534（0xFFFF=广播） |
| **数据类型** | 1-bit 线圈 + 16-bit 寄存器 | 13 种原生类型（bool~float64+string） |
| **自描述性** | 无 | 标签名+类型+扩展属性 |
| **标签发现** | 无 | 0x01 分页查询 |
| **读 1 个 float** | 2 个寄存器 = ~15 字节请求 | ~33 字节（含帧开销） |
| **批量写入** | 逐寄存器或批量寄存器 | 按标签 ID，支持混合类型 |
| **校验** | CRC16（同多项式） | CRC16（同多项式） |
| **广播** | 地址 0，仅写，不回复 | 地址 0xFFFF，仅写，不回复 |
| **心跳** | 无标准方式 | 0x07 含 uptime + 统计 |

### 效率分析

TagBus 相比 Modbus 约 2.2 倍帧开销，换来：

- **零配置** — 主机无需预知寄存器表
- **类型安全** — float 不再需要手动拼两个 16-bit 寄存器
- **可扩展** — 新增标签无需改主机代码，只需重新发现

对 115200 bps 以上的链路，增加的几十字节开销可忽略不计。
