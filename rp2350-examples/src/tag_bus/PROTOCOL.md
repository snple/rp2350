## 1. 范围

本规范定义一种运行在 **RS-485 / UART / USB-CDC / TCP** 等字节流链路上的主从式标签总线协议，提供：

- 设备身份与能力发现；
- 标签（tag）自动枚举与元数据发布；
- 类型安全、可批量、可混合类型的标签读写；
- 广播写入；
- 诊断计数与健康状态。

**不包含**：地址分配流程、固件升级、事件上报、访问控制。见 [§2](#2-设计目标与非目标)。

## 2. 设计目标与非目标

### 2.1 目标

| # | 目标 | 落地方式 |
|---|---|---|
| G1 | 不依赖线路静默即可定界 | 2 字节定界符 `A5 5A` + 显式长度 + CRC-32C；任何时刻从任意字节重新同步 |
| G2 | 类型安全、自描述 | 标签自带类型与访问属性；元数据可机器校验（`MIN`/`MAX`/`ENUM`） |
| G3 | 零会话状态 | 每个请求自包含；无游标、无版本协商状态机、无分页上下文 |
| G4 | 实现不可能越界 | 长度上限在头部即校验；所有响应"要么完整、要么整帧报错" |
| G5 | 面向未来的线格式 | 长度字段 16 位，MTU 是可宣告的能力而非协议常量；升级 MTU 不破坏兼容性 |
| G6 | 可测试 | 协议核心与硬件解耦，可在主机上跑一致性测试 |

### 2.2 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 分片 / 重组 | MTU 2048 + 标签级批量已覆盖所有已知场景；引入重组等于引入会话状态与超时状态机 |
| 事件上报 / 主动推送 | 需要总线仲裁，破坏"单主站轮询"这一最值钱的简化 |
| 多主站 / 设备对等 | 帧内无源地址；需要时由新的 SOF 定义新协议 |
| 认证 / 加密 / 访问控制 | 信任边界在物理层；本协议只保证"不会因链路错误静默写错值" |
| 分页 / 游标 | 单帧容量足够；`TAG_META` 按单标签查询 |
| 动态类型 / 可选长度前缀 | 类型来自元数据，值只带长度 |
| 会话层（连接、心跳保活） | 由主机应用层实现；本协议只提供无状态的 `STATUS` |

## 3. 传输层

### 3.1 字节流

上层把链路视为**双向字节流**。同一帧的全部字节必须按顺序到达；协议不依赖字节间的时间间隔。

适用的物理层：RS-485 半双工、TTL UART、USB-CDC、TCP/串口服务器。任何"会丢字节但不改变字节顺序"的链路都可用。

### 3.2 单主站

总线上**必须**有且仅有一个主机。设备**不得**主动发送任何字节，仅在被正确寻址的请求后发送一个响应。

### 3.3 时序

设波特率为 `baud`，8N1 编码（10 bit/字节）：

```
T_frame(LEN) = (12 + LEN) × 10 / baud
```

| 载荷 LEN | 帧长 | @9600 | @115200 | @921600 |
|---|---|---|---|---|
| 0 | 12 | 12.5 ms | 1.0 ms | 0.13 ms |
| 23 | 35 | 36.5 ms | 3.0 ms | 0.38 ms |
| 257 | 269 | 280 ms | 23.3 ms | 2.9 ms |
| 1024 | 1036 | 1.08 s | 89.9 ms | 11.2 ms |
| 2048 | 2060 | 2.15 s | 178.8 ms | 22.3 ms |

- 设备**必须**在收到请求最后一字节后 `T_turnaround ≤ 5 ms` 内开始发送响应的第一个字节。
- 设备**不得**在请求接收完成之前发送任何字节。
- 主机**应当**在收到响应最后一字节后等待 ≥ 1 ms（RS-485 收发器换向）再发下一帧。
- 主机超时**应当**满足：

```
T_timeout ≥ T_frame(LEN_req) + T_frame(LEN_resp) + T_turnaround + 20 ms
```

推荐默认值：`LEN ≤ 64` 用 100 ms；`LEN ≤ 512` 用 250 ms；`LEN ≤ 2048` 用 600 ms。

### 3.4 前导字节

主机**可以**在定界符前插入 1–3 个 `0xFF` 作为线路稳定前导。接收方**必须**忽略定界符之外的任何字节，因此前导不影响协议。

## 4. 帧格式

### 4.1 总览

```
┌───────┬─────┬───────┬──────┬───────┬─────────┬─────────┐
│  SOF  │ SEQ │  DST  │ FUNC │  LEN  │ PAYLOAD │  CRC32C │
│  2B   │ 1B  │  2B   │ 1B   │  2B   │  LEN B  │   4B    │
└───────┴─────┴───────┴──────┴───────┴─────────┴─────────┘
  偏移0   偏移2  偏移3   偏移5   偏移6    偏移8     偏移 8+LEN
```

### 4.2 字段

| 偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | `SOF` | 2 | **字节序列** | 固定 `A5 5A`。**定义为两个字节，不是 16 位整数**——不存在字节序问题 |
| 2 | `SEQ` | 1 | u8 | 事务序号，主机递增，设备原样回显 |
| 3 | `DST` | 2 | u16 LE | 目标地址，见 [§6.1](#61-地址空间) |
| 5 | `FUNC` | 1 | u8 | 功能码；异常响应为 `FUNC \| 0x80` |
| 6 | `LEN` | 2 | u16 LE | 载荷字节数，`0 ≤ LEN ≤ MTU` |
| 8 | `PAYLOAD` | LEN | — | 功能码相关 |
| 8+LEN | `CRC32C` | 4 | u32 LE | 校验值，覆盖 `SOF` 之后的 `SEQ..PAYLOAD` |

### 4.3 帧长与 MTU

```
帧长 = 12 + LEN
```

- 协议上限：`LEN ≤ 2048`（帧长 ≤ 2060）。
- 每台设备**必须**在 `DEVICE_INFO` 中宣告自己的 `MTU`（可小于 2048）。
- 接收方**必须**在解析到 `LEN` 的**当刻**校验 `LEN ≤ 本机 MTU`；超限即为**帧错误**，**不得**先缓冲再判断。
- 主机**必须**能接收最大 `12 + min(2048, MTU_dev)` 字节的帧。

### 4.4 CRC-32C

| 参数 | 值 |
|---|---|
| 名称 | CRC-32/ISCSI（Castagnoli） |
| 多项式 | `0x1EDC6F41`（正向） / `0x82F63B78`（反射） |
| 初值 | `0xFFFFFFFF` |
| 输入/输出反射 | 是 |
| 结果异或 | `0xFFFFFFFF` |
| 自检值 | `CRC32C("123456789") = 0xE3069283` |
| 覆盖范围 | 帧偏移 **2**（`SEQ`）至载荷末尾，**不含** `SOF`、**不含** CRC 自身 |
| 存储 | u32 小端 |

**为什么是 32 位**：帧长已放宽到 2048 载荷（算上头部 2060 字节）。在劣化线路（BER 1e-6）上 1 KB 帧的损坏率约 0.8%/帧，CRC-16 的残余漏检率约 2⁻¹⁶，折算约每 22 小时出现一次**未被发现的错误**；若该错误落在 WRITE 帧上就是静默写错配置。CRC-32C 把这一数字降到约每 170 年一次。

**实现注记**

- 256 项表占 1 KB flash；16 项半字节表占 64 B（约慢 2 倍，1024 字节在 150 MHz 上仍在 100 µs 以内）。
- **Python 的 `binascii.crc32` 是 CRC-32/ISO-HDLC，不是 CRC-32C**。必须使用 Castagnoli 表（`crcmod`、`google-crc32c` 或自建表），否则第一个上位机就会校验失败。

### 4.5 为什么没有帧尾

v2 使用 `0x7E7E` 作为帧尾。v3 删除它，理由：

1. 长度字段 + CRC 已经唯一确定帧的边界与完整性，帧尾是**纯冗余**（每帧 2–4 字节）。
2. 帧尾引入了一类无法自愈的故障：帧尾损坏时接收方会一直等待"按长度算出来的位置"，只能靠缓冲区溢出重置，从而丢掉后面**完全合法**的帧。
3. 任何对定界格式的变更都**必须**更换 `SOF`（见 [§16](#16-版本与变更策略)），因此定界符本身就是版本家族标识，不需要额外字段。

## 5. 定界与同步恢复

### 5.1 定界符

`SOF = A5 5A` 选取理由：两字节互为按位取反，在随机数据中的自相关性极低；配合 CRC-32C，误判帧的接受概率约为 2⁻³²。

### 5.2 解码器要求

解码器**必须**是逐字节推进的状态机，**必须**满足：

| 要求 | 说明 |
|---|---|
| O(1)/字节 | 不得每收到一个字节就重新扫描整个缓冲区 |
| 失败即丢 1 字节 | 任何校验失败**必须**丢弃当前假设的 `SOF` 的**第一个字节**，立即从其后的字节重新寻找 `SOF`；**不得**等待缓冲区溢出 |
| 有界内存 | 缓冲区需求恰为 `12 + MTU` 字节 |
| 无 panic | 任何输入（含随机流、损坏帧、超长 LEN）**不得**导致 panic、越界或无限等待 |

状态机：

```
HUNT ──0xA5──▶ HUNT_A5 ──0x5A──▶ HEADER(6B) ──LEN≤MTU──▶ PAYLOAD(LEN) ──▶ CRC(4B) ──▶ 交付
  ▲                │                  │ LEN>MTU                                        │
  │                └──非0x5A──────────┤                                                │
  └─────────────────丢 1 字节──────────┴────────────── CRC 失败 ──丢 1 字节────────────┘
```

### 5.3 错误处理矩阵

| 现象 | 设备行为 | 计数 |
|---|---|---|
| `LEN > MTU` | 丢弃 1 字节并重扫，**不响应** | `flags.FRAME` + `err_total` |
| CRC 不符 | 丢弃 1 字节并重扫，**不响应** | `flags.CRC` + `err_total` |
| `SOF` 之后结构不合法（如载荷不足） | 丢弃 1 字节并重扫，**不响应** | `flags.FRAME` + `err_total` |
| `DST` 非本机且非广播 | 按 `LEN` 跳过整帧（**可以**不校验 CRC），**不响应** | 不计数 |
| `DST` 匹配但载荷不合法 | **必须**回异常帧 | `flags.REQ` + `err_total` |
| 广播 + 非 WRITE | 静默丢弃，**不得**回异常帧 | 不计数 |
| 广播 + WRITE | 执行，**不得**发送任何字节 | 条目失败则置 `flags.BC_FAIL` |

> 最后三条是关键区分：**能解析但不合法**→回异常帧；**不该我管**→静默丢弃。广播帧一律不得回应，否则多台设备会同时抢总线。

## 6. 地址与事务模型

### 6.1 地址空间

| 地址 | 含义 |
|---|---|
| `0x0000` | **主机**。所有响应的 `DST` 必须是 `0x0000` |
| `0x0001..0xFFFE` | 设备地址 |
| `0xFFFF` | 广播 |

设备地址**必须**落在 `0x0001..0xFFFE`。这带来一个直接收益：设备收到其他设备的响应帧时（`DST = 0x0000`）天然不匹配，无需角色位或源地址字段即可忽略。

`0x0000` **不是**广播地址（v2 文档曾同时把 `0x0000` 和 `0xFFFF` 定义为广播，实现只认后者——v3 明确取消这一歧义）。

### 6.2 SEQ

- 主机**必须**为每个请求分配 `SEQ`，并在每次新请求时递增（模 256；回绕合法）。
- 设备**必须**在响应中原样回显 `SEQ`，**异常帧也不例外**。
- 主机**必须**丢弃 `SEQ` 与当前未决请求不匹配的响应。
- 设备**不得**因 `SEQ` 重复而拒绝请求（`WRITE` 幂等，见 §6.4）。
- 设备**可以**（非必须）缓存上一次响应并在收到相同 `SEQ` + 相同载荷时重放。

`SEQ` 只解决一件事：**超时重传后，迟到的旧响应不会被误当成新响应**。这是它存在的唯一理由，因此不需要更多状态。

### 6.3 单未决请求

一个主机**不得**在一个端口上同时存在多个未决请求（即禁止流水线）。v3.0 不定义流水线能力位，因此该限制无条件适用。

### 6.4 重传与幂等

- 超时后主机**可以**用**相同的 `SEQ` 和相同的载荷**重传；总尝试次数**不应**超过 3 次。
- **`WRITE` 必须幂等**：写入与当前值相同的值**不得**产生任何额外副作用（除内部持久化计数外）。
- `READ`/`TAG_LIST`/`TAG_META`/`DEVICE_INFO`/`STATUS` 天然幂等。

### 6.5 广播

- 只有 `WRITE`（`0x05`）允许广播，其他功能码的广播帧**必须**被静默丢弃。
- 广播帧**不得**产生任何响应，也不得产生异常帧。
- 广播帧仍占用一个 `SEQ`（主机的序号空间保持单调）。
- 主机**应当**随后用 `READ` 读回确认广播结果。

## 7. 响应与异常

### 7.1 正常响应

`FUNC` 与请求相同，`DST = 0x0000`，`SEQ` 回显，载荷见 [§9](#9-功能详解)。

### 7.2 异常响应

```
FUNC  = 请求的 FUNC | 0x80
LEN   = 1
载荷   = status(1)
```

异常帧**必须**回显 `SEQ`，且**必须**对广播帧禁用。

### 7.3 帧级错误与条目级错误

这是本协议最容易用错的地方，必须严格区分：

| 级别 | 触发 | 表达方式 |
|---|---|---|
| **帧级** | 整条命令无法执行：未知功能码、载荷结构非法、条目数超限、设备忙、内部错误、`TAG_META` 的目标不存在 | **异常帧**（`FUNC\|0x80`） |
| **条目级** | 命令可以执行，但个别标签失败：标签不存在、只读、类型不符、越界、写失败、值不可用 | **条目内的 `status` 字节** |

例：`READ` 请求 3 个标签，其中 1 个不存在 → 正常响应，3 个条目，缺失的那个 `status = NOT_FOUND`。`READ` 请求 5000 个标签 → 异常帧 `TOO_MANY_ITEMS`。

## 8. 功能码总览

| 码 | 名称 | 方向 | 广播 | 说明 |
|---|---|---|---|---|
| `0x01` | `DEVICE_INFO` | 读 | 否 | 身份、能力、MTU、标签表版本 |
| `0x02` | `TAG_LIST` | 读 | 否 | 标签清单（id / 类型 / 访问），单帧全量 |
| `0x03` | `TAG_META` | 读 | 否 | **单个**标签的完整元数据（按 id） |
| `0x04` | `READ` | 读 | 否 | 批量读任意标签的值 |
| `0x05` | `WRITE` | 写 | **是** | 批量写标签值 |
| `0x06` | `STATUS` | 读 | 否 | 健康状态 + 粘滞错误位图 |

`0x07..0x7F` 保留给未来功能码（**追加是向后兼容的**）。`0x80 | FUNC` 专用于异常响应，故有效功能码 ≤ `0x7F`。

**编号不沿用 Modbus**：Modbus 的 `0x06` 是"写单个寄存器"，与其让 `0x06` 一号两义，不如整体重排并在 [附录 A](#附录-a与-modbus-rtu-对比) 给出对照。

## 9. 功能详解

### 9.1 `0x01` DEVICE_INFO

**请求**：`LEN` **必须**为 0。

**响应载荷**（`28 + name_len` 字节）：

| 偏移 | 字段 | 长度 | 说明 |
|---|---|---|---|
| 0 | `proto_major` | 1 | 本规范为 `3` |
| 1 | `proto_minor` | 1 | 本规范为 `0` |
| 2 | `func_mask` | 2 | 位图：bit *N* = 支持功能码 *N*（bit 0 恒 0） |
| 4 | `vendor_id` | 2 | 厂商编号 |
| 6 | `product_id` | 2 | 产品型号 |
| 8 | `serial` | 8 | 设备唯一序列号（同一厂商内唯一） |
| 16 | `fw_major` / `fw_minor` / `fw_patch` | 1+1+1 | 固件语义化版本 |
| 19 | `max_items` | 2 | 单请求最大条目数 |
| 21 | `mtu` | 2 | 本机载荷上限，`≤ 2048` |
| 23 | `tag_gen` | 2 | 标签表版本，表变化时**必须**递增（模 65536） |
| 25 | `tag_count` | 2 | 标签总数 |
| 27 | `name_len` | 1 | 设备名长度，`≤ 64` |
| 28 | `name` | n | 设备名，UTF-8 |

**`func_mask` 取代了帧头版本号**：主机据此精确判断可用命令，而不是猜"这一代大概支持什么"。

**示例**（`vendor=1, product=2, serial=A1B2…0718, fw=0.1.0, max_items=32, mtu=2048, tag_gen=1, tag_count=6`）：

```
03 00  7E 00  01 00  02 00  A1 B2 C3 D4 E5 F6 07 18  00 01 00  20 00  00 08  01 00  06 00  0D  54 61 67 42 75 73 20 44 65 76 69 63 65
```

### 9.2 `0x02` TAG_LIST

**请求**：`LEN` **必须**为 0（单帧全量枚举，不分页）。

**响应载荷**：

```
count(2) + [ id(2) + type(1) + access(1) ] × count
```

| 字段 | 说明 |
|---|---|
| `count` | 标签总数；**必须**等于 `DEVICE_INFO.tag_count` |
| `type` | [§10](#10-数据类型) 的类型编码 |
| `access` | 位掩码：`0x01 = 可读`、`0x02 = 可写`；故 `RO = 0x01`、`RW = 0x03` |

设备**必须**保证 `2 + 4×count ≤ MTU`（在注册阶段校验），因此**永远不会**出现截断。`MTU = 2048` 时可容纳 511 个标签。

**分层原则**：清单只携带"组轮询表所需"的信息。名称、单位、量程属于元数据，按需用 `TAG_META` 取——这正是"元数据不需要分页"的前提。

**示例**（6 个标签）：

```
06 00  64 00 11 01  65 00 11 01  66 00 01 01  C8 00 11 03  C9 00 01 03  CA 00 21 01
```

### 9.3 `0x03` TAG_META

**请求载荷**：`id(2)`，`LEN` **必须**为 2。

**响应载荷**：

```
id(2) + type(1) + access(1) + attr_len(2) + attrs(attr_len)
```

- `id` 不存在 → **异常帧** `NOT_FOUND`。
- `id/type/access` 与 `TAG_LIST` 重复是**故意的**：该响应可独立解析，抓包与日志无需上下文。
- 设备**必须**保证 `6 + attr_len ≤ MTU`（注册阶段校验），因此元数据**永远不会在请求时**被重新编码或截断。

**示例 1**：温度（`id=100`, F32, RO，量程 10~35 ℃）

```
64 00  11 01  19 00  01 06 E6 B8 A9 E5 BA A6  02 03 E2 84 83  03 04 00 00 20 41  04 04 00 00 0C 42
```

**示例 2**：状态（`id=102`, BOOL, RO，枚举 0=关 / 1=开）

```
66 00  01 01  15 00  01 06 E7 8A B6 E6 80 81  05 0B 02 00 03 E5 85 B3  01 03 E5 BC 80
```

### 9.4 `0x04` READ

**请求载荷**：

```
count(2) + [ id(2) ] × count
```

- `count = 0` → **异常帧** `BAD_REQUEST`（不定义"读全部"，避免歧义与爆炸性响应）。
- `count > max_items` → **异常帧** `TOO_MANY_ITEMS`。

**响应载荷**：

```
count(2) + [ id(2) + status(1) + len(1) + value(len) ] × count
```

- 条目**必须**与请求的 id **一一对应且顺序相同**（含失败条目）。
- `READ` **不检查访问属性**：只读标签与可读写标签都能读。
- `len` 恒为 1 字节 → 单值最大 255 字节。
- `status = UNAVAILABLE (0x07)` 表示该标签当前无有效值（传感器断线等），此时 `len = 0`。
- 若响应无法装进 `MTU`，设备**必须**回整帧异常 `TOO_MANY_ITEMS`，**不得**部分返回。

**示例**（读 100/101/102）：

请求载荷 `03 00  64 00  65 00  66 00`

响应载荷 `03 00  64 00 00 04 00 00 D0 41  65 00 00 04 00 00 48 42  66 00 00 01 01`

### 9.5 `0x05` WRITE

**请求载荷**：

```
count(2) + [ id(2) + len(1) + value(len) ] × count
```

- `count = 0` → **异常帧** `BAD_REQUEST`。
- 广播：`DST = 0xFFFF`，**不得**产生任何响应。

**响应载荷**：

```
count(2) + [ id(2) + status(1) ] × count
```

- 条目**必须**与请求一一对应且顺序相同。

**校验顺序**（设备**必须**按此顺序，返回第一个失败原因）：

1. 标签不存在 → `NOT_FOUND`
2. 标签不可写 → `READ_ONLY`
3. 值长度/编码与类型不符 → `TYPE_MISMATCH`
4. 超出 `MIN`/`MAX`（若已声明）→ `OUT_OF_RANGE`
5. 硬件写入钩子失败 → `WRITE_FAILED`
6. 全部通过 → `OK`

**原子性**：批量写是**非原子**的。设备按请求顺序逐条处理，每条独立成功或失败，并逐条返回状态。主机**不得**假设回滚。

**幂等性**：写入与当前值相同的值**不得**产生额外副作用。

**示例**（写 201=true, 200=28.0 ℃）：

请求载荷 `02 00  C9 00 01 01  C8 00 04 00 00 E0 41`

响应载荷 `02 00  C9 00 00  C8 00 00`

**广播示例**（仅写 200=28.0 ℃，无响应）：

`01 00  C8 00 04 00 00 E0 41`

### 9.6 `0x06` STATUS

**请求**：`LEN` **必须**为 0。

**响应载荷**（12 字节）：

| 偏移 | 字段 | 长度 | 说明 |
|---|---|---|---|
| 0 | `state` | 1 | 当前健康状态：`0x00` 正常 / `0x01` 告警 / `0x02` 故障。反映**当前**条件，不锁存 |
| 1 | `flags` | 1 | 自上次复位以来**曾经**发生过的错误类型（粘滞位图，见下） |
| 2 | `uptime_s` | 4 | 运行秒数，u32 回绕 |
| 6 | `rx_ok` | 4 | 成功处理的请求帧数（发给本机的单播 + 广播写入） |
| 10 | `err_total` | 2 | 自上次复位以来的错误帧总数，饱和于 `0xFFFF` |

**`flags` 位定义**（粘滞：置位后保持到下次复位；只读）

| 位 | 名称 | 置位条件 |
|---|---|---|
| 0 | `CRC` | 任一 CRC 校验失败的帧（**含其他设备的帧**，反映线路质量） |
| 1 | `FRAME` | 结构非法：`LEN > MTU`、载荷不足、字段不完整 |
| 2 | `REQ` | 请求语义非法：未知功能码、载荷格式错误、`count = 0`、预算不足 |
| 3 | `BC_FAIL` | 至少一次广播写中出现条目失败（条目级结果不计数） |
| 4..7 | 保留 | **必须**为 0 |

**语义约束**

- `flags` **必须**粘滞且**不得**读后清零：`STATUS` 必须幂等（[§6.4](#64-重传与幂等)），读后清零会让重传产生副作用。粘滞位 + `uptime_s` 已足够回答"本次运行是否见过异常"。
- `err_total` 与 `rx_ok` 一起给出误码规模：链路错误率 ≈ `err_total / (rx_ok + err_total)`。
- `err_total` 只统计 `flags` 中 `CRC`/`FRAME`/`REQ` 三类对应的**帧**；`BC_FAIL` 是条目级，只置位不计数。
- u16 计数器**必须**饱和（不回绕）；u32 计数器**可以**自由回绕。

**刻意不提供的信息**

| 不提供 | 理由 |
|---|---|
| `tx_ok` | 主机本来就能观察到应答有无；且数值 ≈ `rx_ok` |
| `reset_cause` | 复位可由 `uptime_s` 骤减发现；具体原因属于本地日志，不必占用总线 |
| 地址不匹配计数 | 多站总线上每台设备都会收到别人的帧，该计数永远是常数噪声 |
| `bc_ok` / `bc_bad` 条目数 | 广播结果主机应当用 `READ` 读回；只需 `BC_FAIL` 提示"曾经失败过" |
| 分类型错误计数 | 由 `flags`（哪一类）+ `err_total`（共多少）组合表达，避免 6 个并行计数器 |

## 10. 数据类型

| 编码 | 名称 | 值长度 | 说明 |
|---|---|---|---|
| `0x01` | BOOL | 1 | 仅接受 `0x00` / `0x01`；其他值写入时判 `TYPE_MISMATCH` |
| `0x02` | NULL | 0 | 保留。**不使用它作为标签类型**，值缺失用 `UNAVAILABLE` 表达 |
| `0x11` | F32 | 4 | IEEE 754，小端 |
| `0x12` | F64 | 8 | IEEE 754，小端 |
| `0x13` | I32 | 4 | 小端 |
| `0x14` | I64 | 8 | 小端 |
| `0x15` | U32 | 4 | 小端 |
| `0x16` | U64 | 8 | 小端 |
| `0x17` | I8 | 1 | |
| `0x18` | U8 | 1 | |
| `0x19` | I16 | 2 | 小端 |
| `0x1A` | U16 | 2 | 小端 |
| `0x21` | STRING | n | UTF-8，`n ≤ 255` |
| `0x22` | BYTES | n | 原始字节，`n ≤ 255` |
| `0x41` | TIMESTAMP | 8 | Unix 秒，u64 小端 |
| `0x42` | ID | 12 | `ts[6] + count[2] + random[4]`，小端 |

编码与 NSON 二进制格式保持一致。`0x31`(ARRAY) / `0x32`(MAP) 不在本协议范围内。

- 所有多字节值**必须**小端。
- 定长类型的值长度**必须**等于表中长度，否则 `TYPE_MISMATCH`。
- 变长类型上限 255（由条目 `len` 字段的位宽决定）。

## 11. 标签元数据与属性

### 11.1 三层模型

| 层 | 命令 | 内容 | 使用者 | 频率 |
|---|---|---|---|---|
| 清单 | `TAG_LIST` | `id + type + access` | 主机组建轮询表 | 上线、`tag_gen` 变化时 |
| 元数据 | `TAG_META` | 名称/单位/量程/枚举/默认值 | 人机界面、写入校验 | 按需 |
| 值 | `READ`/`WRITE` | 只有字节 | 数据面 | 高频 |

**结论**：主机不需要读取任何元数据就能把设备跑起来。元数据只在需要展示或需要设备侧校验时才取。

### 11.2 固定骨架

```
id(2) + type(1) + access(1) + attr_len(2) + attrs(attr_len)
```

固定部分**只有这四个字段，永不扩展**。所有未来需求都走属性，因此固定骨架的布局可以永久冻结。

### 11.3 属性编码（TLV）

```
attr := tag(1) + len(1) + value(len)
```

- `len` 为 1 字节 → 单个属性值 ≤ 255 字节。
- **名称也是属性**（`0x01`），不做特例。看似多花 2 字节，但避免了"以后每个变长字段都想学 `name_len`"的滑坡。
- 设备**应当**按 `tag` 升序输出（便于字节比对与测试）；主机**不得**依赖顺序。
- 属性标签**必须**唯一；主机取第一个，设备**不得**发送重复项。
- 主机**必须**跳过不认识的属性标签。

### 11.4 属性目录

| tag | 名称 | 编码 | 出现 | 说明 |
|---|---|---|---|---|
| `0x01` | `NAME` | UTF-8 | **必须** | 标签显示名。建议 ≤ 64 字节 |
| `0x02` | `UNIT` | UTF-8 | 可以 | 物理单位，如 `"℃"`。建议 ≤ 16 字节 |
| `0x03` | `MIN` | 标签类型的定长编码 | 可以 | 允许下限（含） |
| `0x04` | `MAX` | 标签类型的定长编码 | 可以 | 允许上限（含） |
| `0x05` | `ENUM` | `count(1) + { value(定长) + label_len(1) + label } × count` | 可以 | 枚举标签 |
| `0x06` | `DEFAULT` | 标签类型的定长编码 | 可以 | 复位值/出厂值 |
| `0x07..0x7F` | 保留 | — | 不得 | 未来核心属性 |
| `0x80..0xBF` | 厂商自定义 | — | 可以 | 含义由 `vendor_id` + `product_id` 界定 |
| `0xC0..0xFF` | 保留 | — | 不得 | |

**为什么 `MIN`/`MAX` 用类型的定长编码而不是字符串**：v2 用 `"min:10,max:35"` 自由文本，主机必须自己解析浮点数（精度、locale、非法输入全是坑），设备也无法可靠校验。定长编码让范围和值使用同一套解码器，比较是精确的。

**为什么 `ENUM` 是结构化的而不是 `"0:关,1:开"`**：自由文本在标签里出现 `,` 或 `:` 时无法解析，需要引入转义规则；而且无法表达 `0.5:半速` 这类浮点枚举。结构化编码里每条记录的 `value` 是定长的，**不需要任何转义**。

**刻意不定义的属性**：`scale`/`offset`（设备必须直接输出工程量值）、`decimals`（纯展示）、`description`（文档的事）、`poll_hint`（非数据面必需）、`persist`（设备行为）。

> 属性是可跳过的扩展点，**追加属性永远是向后兼容的**，所以现在只定义数据面必需的那几个；将来需要再加，不必等大版本。

### 11.5 类型化值规则

1. `MIN`/`MAX`/`DEFAULT` **必须**使用标签自身类型的编码（小端、定长），与 `READ` 返回的值完全一致。
2. `MIN`/`MAX`/`DEFAULT` 只允许用于**定长类型**。对 `STRING`/`BYTES` 声明它们是设备配置错误，注册时必须拒绝。
3. `ENUM` 只允许用于**定长类型**；每条 `value` 的长度等于该类型的定长。
4. `ENUM` 的 `count ≥ 1`，`label` 为合法 UTF-8 且非空，`value` 互不相同。
5. 若同时存在 `MIN`/`MAX`，必须满足 `MIN ≤ MAX`；`DEFAULT` 必须落在区间内。
6. 浮点比较：`MIN`/`MAX` 为闭区间；`NaN` **必须**判为 `TYPE_MISMATCH`。

### 11.6 尺寸预算

设备**必须**在**注册阶段**（而非请求阶段）校验：

```
6 + attr_len ≤ MTU                     # TAG_META 响应可容纳
2 + 4 × tag_count ≤ MTU                # TAG_LIST 响应可容纳
```

违反任一条件的标签**必须**注册失败。这从结构上消除了"响应装不下 → 缓冲区越界"这一整类缺陷。

推荐（非强制）上限：`NAME ≤ 64B`、`UNIT ≤ 16B`、`ENUM ≤ 24 条`、每条 `label ≤ 24B`。按此计算最坏情况元数据约 915 字节，`MTU = 2048` 可容纳。

## 12. 状态码

| 码 | 名称 | 级别 | 含义 |
|---|---|---|---|
| `0x00` | `OK` | 条目 | 成功 |
| `0x01` | `NOT_FOUND` | 两者 | 标签 ID 不存在 |
| `0x02` | `READ_ONLY` | 条目 | 尝试写入只读标签 |
| `0x03` | `TYPE_MISMATCH` | 条目 | 值长度/编码与类型不符，或 BOOL 值非法，或为 NaN |
| `0x04` | `OUT_OF_RANGE` | 条目 | 超出 `MIN`/`MAX` |
| `0x05` | `WRITE_FAILED` | 条目 | 硬件写入钩子失败 |
| `0x06` | `UNKNOWN_FUNC` | 帧 | 不支持的功能码 |
| `0x07` | `UNAVAILABLE` | 条目 | 值当前不可用（传感器断线等），此时 `len = 0` |
| `0x08` | `BAD_REQUEST` | 帧 | 载荷结构非法（长度、字段数、`count = 0` 等） |
| `0x09` | `TOO_MANY_ITEMS` | 帧 | 条目数超 `max_items`，或响应无法装入 `MTU` |
| `0x0A` | `BUSY` | 帧 | 设备暂时无法处理，请稍后重试 |
| `0x0B` | `INTERNAL` | 帧 | 设备内部错误 |

`NOT_FOUND` 在两种级别都出现：`TAG_META` 找不到目标时是整帧错误；`READ`/`WRITE` 中某个条目找不到时是条目错误。

## 13. MTU、批大小与时延

### 13.1 MTU 协商

- 协议上限 2048；设备在 `DEVICE_INFO.mtu` 中宣告实际值。
- 主机请求载荷**不得**超过 `min(2048, mtu_dev)`。
- 设备的响应载荷**不得**超过自己的 `mtu`。
- 提升协议上限（如 4096）**不是**破坏性变更：`LEN` 已是 16 位。

### 13.2 批大小

- `max_items` 是设备保证能处理的**条目数**上限（不保证字节预算）。
- 变长类型（`STRING`/`BYTES`）仍可能因字节预算触发 `TOO_MANY_ITEMS`；主机**应当**在收到该错误后减半重试。
- 轮询场景**应当**把载荷控制在 256 字节以内：一帧 2048 字节在 115200 下要 179 ms，丢失一帧的重传代价很高。

### 13.3 单帧容量（`MTU = 2048`）

| 命令 | 请求最多 | 响应最多 |
|---|---|---|
| `TAG_LIST` | — | 511 个标签 |
| `TAG_META` | — | 单标签，属性区 ≤ 2042 |
| `READ` | 1023 个 id | 视值长度：`U8` 409 条、`F32` 255 条、`STRING(255)` 7 条 |
| `WRITE` | 视值长度；`F32` 约 290 条 | 682 条 |

## 14. 设备符合性要求

设备实现**必须**满足：

1. 地址在 `0x0001..0xFFFE`；只响应 `DST` 等于本机或 `0xFFFF` 的帧。
2. `DEVICE_INFO` 布局永久固定，且**必须**支持。
3. 解码器满足 [§5.2](#52-解码器要求)：O(1)/字节、失败丢 1 字节、有界内存、无 panic。
4. `LEN > 本机 MTU` 在解析到 `LEN` 的当刻判错，不缓冲。
5. 所有响应"要么完整、要么整帧报错"，不得部分返回。
6. `READ`/`WRITE` 的响应条目与请求 id 一一对应且**顺序相同**。
7. `SEQ` 原样回显，异常帧也回显。
8. 广播帧只执行 `WRITE`，且**绝不**发送任何字节。
9. 帧级错误用异常帧（`FUNC|0x80`），条目级错误用条目 `status`，不得混用。
10. `WRITE` 校验顺序严格按 [§9.5](#95-05-write)，且幂等。
11. 注册阶段校验 `6 + attr_len ≤ MTU` 与 `2 + 4×tag_count ≤ MTU`，违反即注册失败。
12. 标签 ID 唯一；重复注册必须失败。
13. `tag_gen` 在标签表变化时递增。
14. 计数器与 `flags` 语义严格按 [§9.6](#96-06-status)：`err_total` 饱和、`flags` 粘滞且只在复位时清除。
15. `uptime_s` 用真实时间基准维护（如毫秒节拍），不得用循环迭代次数近似。
16. 计数器与状态在异常路径上也不得丢失（除复位外）。

---

## 15. 主机符合性要求

1. 上线后**第一条命令必须是** `DEVICE_INFO`；据此获得 `func_mask`、`max_items`、`mtu`、`tag_gen`、`tag_count`。
2. 只使用 `func_mask` 声明支持的功能码。
3. 每次请求递增 `SEQ`，并丢弃 `SEQ` 不匹配的响应。
4. 同一端口上**不得**有多个未决请求。
5. 超时按 [§3.3](#33-时序) 计算；重传**必须**复用同一 `SEQ` 与相同载荷，总尝试 ≤ 3 次。
6. 请求载荷 ≤ `min(2048, mtu_dev)`；响应缓冲区 ≥ `12 + min(2048, mtu_dev)`。
7. 元数据解析**必须**跳过未知属性标签。
8. 广播写之后**应当**用 `READ` 读回确认。
9. 帧校验**必须**用 CRC-32C（Castagnoli），不得用 `binascii.crc32` 之类的 ISO-HDLC 实现。
10. `tag_gen` 变化时**必须**重新枚举标签表。

## 16. 版本与变更策略

| 变更类型 | 是否破坏兼容 | 手段 |
|---|---|---|
| 新增功能码 | 否 | 用保留码；主机经 `func_mask` 判断 |
| 新增属性 | 否 | 主机跳过未知属性 |
| 提升 `MTU` 上限 | 否 | `LEN` 已 16 位；未超本机 `MTU` 即可 |
| 修改既有功能码的语义/载荷布局 | **是** | 禁止 |
| 修改帧头布局或 CRC 算法 | **是** | **必须更换 `SOF`**，视为新协议家族 |
| 修改地址语义 | **是** | 必须更换 `SOF` |

**定界符即家族标识**：`A5 5A` 专属 TagBus v3 家族。任何不兼容的线格式变更必须选一个新的 `SOF`，而不是在帧头里加版本号。理由：版本号只有在双方都能解析头部时才有意义，而头布局本身就是最容易变的部分。

**版本号的唯一位置**：`DEVICE_INFO.proto_major/proto_minor`，用于日志、诊断与文档对应。本文件 = 协议 3.0 / 文档修订 2025-10。

**功能码语义一旦发布永久冻结**。v2 的教训是 `0x06` 同时被解释为"设备信息"和 Modbus 的"写单寄存器"。

## 附录 A：与 Modbus RTU 对比

| 维度 | Modbus RTU | TagBus v3 |
|---|---|---|
| 帧定界 | 3.5 字符静默 | `A5 5A` + 显式长度 + CRC-32C |
| 最大帧 | 256 字节 | 2060 字节 |
| 寻址 | 1..247，0 = 广播 | 1..65534；`0x0000` = 主机，`0xFFFF` = 广播 |
| 事务关联 | 无（靠时序） | `SEQ` 字节 |
| 校验 | CRC-16 | CRC-32C |
| 数据类型 | 16 位寄存器 / 位 | 16 种原生类型 |
| 自描述 | 无 | 清单 + 元数据 + 类型化量程 |
| 错误表达 | 功能码最高位置 1 | 同样用 `FUNC\|0x80`，但载荷固定 1 字节状态码 |
| 批量写 | 写多寄存器 `0x10` | `WRITE`（支持混合类型、逐条状态） |
| 心跳/诊断 | 无标准 | `STATUS`，粘滞错误位图 + 饱和计数 |
| 事务状态 | 无 | 无（单未决请求） |

**注意**：v3 的功能码**不**沿用 Modbus 编号（Modbus `0x06` = 写单寄存器）。若从 Modbus 迁移，请按上表对应关系重写，不要按编号猜。

## 附录 B：从 v2 迁移

### B.1 编码映射

| v2 | v3 |
|---|---|
| 帧头 `A55A`（u16 LE ⇒ 线上 `5A A5`） | `SOF` 字节序列 `A5 5A`（**线上顺序改变**） |
| 无 | `SEQ`（新增） |
| 设备 ID（`0xFFFF` 广播；文档另称 `0x0000` 也是广播） | `DST`（`0x0000` 主机 / `0xFFFF` 广播，语义唯一） |
| `载荷长度` u16 | `LEN` u16（上限 1024 → 2048） |
| CRC-16 (Modbus) | CRC-32C |
| 帧尾 `7E7E` | **删除** |
| `0x01` 读标签列表（分页） | `0x02` `TAG_LIST`（单帧全量） |
| `0x02` + `0x03` 读值（按 access 拆分） | `0x04` `READ`（不区分 access） |
| `0x05` 写值 | `0x05` `WRITE` |
| `0x06` 设备信息 | `0x01` `DEVICE_INFO`（+ `func_mask`/`serial`/`max_items`/`mtu`/`tag_gen`） |
| `0x07` 心跳 | `0x06` `STATUS`（粘滞位图 + 饱和计数） |
| 元数据 `name_len + name + ext_len + ext` | 固定骨架 + TLV 属性（`NAME` / `UNIT` / `MIN` / `MAX` / `ENUM` / `DEFAULT`） |
| `key:value,` 自由文本扩展 | TLV，其中 `ENUM` 为结构化记录 |
| 无 | `UNAVAILABLE` 条目状态（表达"值缺失"） |

### B.2 v2 已确认缺陷及其在 v3 中的处理

| v2 缺陷（实测） | v3 处理 |
|---|---|
| 文档要求扫描 `A5 5A`，线上实际是 `5A A5` | `SOF` 定义为字节序列，且线上即 `A5 5A` |
| `RX_BUF_SIZE(512) < 最大帧(1035)`，合法最大帧永远收不到 | MTU 参数化，缓冲 = `12 + MTU`，单一来源 |
| `TagMeta::new` 截断名称但记录原始长度 → 响应构造越界 panic | 元数据注册期预编码 + 尺寸断言，运行期零编码 |
| `0x01` 响应无容量预算 → 32 标签时越界 panic | 注册期断言 `2 + 4×tag_count ≤ MTU` |
| 坏帧尾后无法重同步，后面合法帧全丢 | 取消帧尾；任何失败丢 1 字节重扫 |
| `0x0000` 广播语义自相矛盾 | `0x0000` = 主机，广播仅 `0xFFFF` |
| 文档 v4.1 / 线上 2.0 / 示例 v2.0 三处不一致 | 版本只在 `DEVICE_INFO` 一处；文档修订独立编号 |
| §12 示例的 4 处载荷长度全错 | 附录 C 的全部帧由脚本计算 CRC 生成 |
| 类型码范围写成 `0x01-0x0D`、类型数写成 13 | [§10](#10-数据类型) 16 个编码，唯一一张表 |
| `OUT_OF_RANGE` 定义但从未实现（996.0 写入 min:10,max:35 返回 OK） | `MIN`/`MAX` 为类型化属性，校验顺序强制 |
| NULL 语义不闭环（无法表达"值缺失"） | 条目状态 `UNAVAILABLE` |
| `0x03` 读只读标签返回 `READ_ONLY` | `READ` 不检查访问属性 |
| `0x02`/`0x03` 功能重复 | 合并为 `READ` |
| `error_count` 一个计数器包打天下、语义不明 | `flags` 粘滞位图 + `err_total`；且明确不统计发往其他设备的帧 |
| 重复标签 ID 静默取第一个 | 注册期拒绝 |
| `access` 不是位掩码（`RW` 不含读位） | `READ`/`WRITE` 位掩码 |
| `uptime` 用主循环迭代次数近似 | `uptime_s` 必须用真实时基 |
| 无序列号，同型号设备无法区分 | `DEVICE_INFO.serial(8)` |

### B.3 不迁移的东西

v2 的 `PROTOCOL-V2.md` 保留仅为说明现存 `tag_bus.rs` 的行为。v3 实现完成后该文件可删除；**不做 v2/v3 双栈**（无外部用户，双栈是纯负担）。

## 附录 D：实现结构要求

规范之外，以下是对实现的**结构性**要求（不是风格偏好）：

1. **协议核心与硬件解耦**：协议层不得依赖 HAL/PAC，必须能作为普通 crate 在主机上 `cargo test`。
2. **解码器是状态机**，不是"每字节扫全缓冲"。
3. **受检写入**：编码器所有 `put_*` 返回 `Result`；禁止裸切片索引与 `as` 截断（用 clippy `deny` 固化）。
4. **元数据注册期预编码**：`TagMeta` 不保存定长字符数组，保存已编码的属性 blob；`TAG_META` 处理 = 写头 + 拷贝。
5. **MTU 单一来源**：`MTU` 只在一处定义，缓冲区尺寸、注册校验、批量预算全部派生自它。
6. **处理器统一签名**：`fn(&[u8], &Registry, &mut Encoder) -> Result<(), Status>`，不允许任何 `panic!`。
7. **计数器饱和**，且在任何异常路径上都不丢失。
8. **测试矩阵**：黄金向量（双向）· 长度 ≤ 3 的穷举字节流 · 随机流不 panic · 合法帧逐字节翻转后必须在 `LEN+12` 字节内重新同步 · 每个状态码至少一条用例 · 会话级脚本测试 · Python 参考主机与 Rust 实现字节级互通。
